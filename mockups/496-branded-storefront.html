One SAME template, two brands, no leak between them

The one inputThree fields, one screen: logo, display name, one accent colour — the same settings card for every client (left panel above), backed by one new jsonb field (tenants.settings.commerce.branding or a sibling under catering, exact key for Core to land — no migration, gap 7 in customer-app.md §5). No per-page branding, no separate colour for checkout vs. confirmation vs. email — one brand object read everywhere that client's customer looks.
Where it rendersThe storefront header (logo tile + name), every button and active chip (currently a hardcoded green in /store/[slug]'s CSS), the confirmation screen's own logo mark, and the receipt email's header band and accent rule — six render sites reading one object, not six copies of a colour.
No cross-tenant leakShopkiraana's panels never mention GIF and GIF's panels never mention Shopkiraana — each tenant's storefront is generated from that tenant's own row only, the same isolation the public routes already enforce by slug. There is no "browse other Veritill stores" anywhere, matching Rule 2 exactly: no "my businesses" list surfaces inside a client's own store.
"Powered by Veritill" is real, optionalShown above with it ON (Shopkiraana, left phone/email) and OFF (GIF, right phone/email) — the exact same code path, one boolean, not two different footers to build and keep in sync.

Against the eight screens.md §0 checks

1. One jobUnchanged from the shipped screens (#239 for /store, the existing /order) — this phase changes only header/accent/logo/footer, never the flow or the action visible on each step.
2. No paragraphsThe settings card is three labelled rows plus one toggle, no explanatory text beyond the twelve-word captions already used elsewhere in Settings.
3. Icon on every rowThe logo tile IS the icon for "this business" everywhere it appears — header, confirmation, email — the same image, never a different mark for the same business on two screens (the exact rule check 3 already states for every other picture in the product).
4-8Unaffected — this phase adds no new screen (the settings card is a new row on the existing Settings → Business profile area, not a new page) and no new step in either storefront's flow.
  • No real logo asset exists yet for either Shopkiraana or GIF in this codebase — the tiles above are placeholder initials in the brand colour, exactly what the real screen shows before a client uploads one (the same "SK"/"GIF" fallback a person's own initials avatar already uses elsewhere in the product).
  • One colour, not a full theme. This phase reads one accent colour, not a full light/dark palette — matching gap 7's own size (S) in customer-app.md. A client who wants their own font or a second colour is a bigger, unscoped ask, named as a later follow-up if Kiran wants it, not guessed here.
  • The domain (shop.<client-domain>) is issue #498, not this one — the slug in the URL bar (/store/shopkiraana) stays a Veritill-hosted path in this phase; a client's own domain is the next approved gap.
