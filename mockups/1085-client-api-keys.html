What this changes (one panel on the existing Admin › Clients list — no new route)

TodayThis mockup
A client row carries a chip "API access: on/off" and an Enable / Turn off button (issue #1046, apps/web/src/app/admin/page.tsx).The chip becomes one tap — "API on · 2 keys ▸" / "API off ▸" — that expands the panel under that client's own row (phone 2); the switch moves into the panel's first line with the plan it bills against (caching §4.11). Same route, same list.
tenants.api_key: one unscoped key for the whole business, read and rotated by the client's owner on Settings → Business (ApiKeyCard.tsx).Keys are rows of the panel, one per integration: a picture for the integration, the name, what it may read in plain words, the three limits, when it was last used, calls this month, Revoke. Nothing here is on the client's side — the owner's card stays behind the entitlement until the later self-service view is deliberately opened (security.md §4).
No way to grant less than everything."New key" is two short screens: name + what it may read (the 8 grantable groups, Off / Read / Write each; the 4 never-grantable ones folded into one locked line, ⓘ says why), then three limits as chips. "Create key" goes through the shipped "Confirm it's you" sheet (S1: an API key is an Approve-class action) and the key is shown exactly once with a copy button; Done is disabled until it is copied.
Reveals audited as tenant.api_key_read.One line on the panel says so — "Every key shown or stopped is recorded · N this month ▸" — and opens the rows inline (phone 7): who, which key, what, when. Revoke is the same confirm dialog the list already uses for Suspend/Cancel, then the step-up sheet.

Customer words, never machine words

"What it may read / may write" (not scopes), "calls a minute" (not rate limit), "rows a page" (not page cap), "stops working on" (not expiry), "used" (not last_used_at), "made by" (not created_by), "stopped" (not revoked_at), "shown" (not api_key_read). The 12 group names are caching §4.11's own customer words, verbatim. The two ⚠ notes on the picker ("includes recipes", "includes costs") are §4.11's own two warnings — the gold and the money.

The one real choice for Kiran — the picker's shape (step 1 of New key)

A (phone 3, recommended): the 8 grantable groups as rows, Off / Read / Write each. Why: it is the product's own list, every grant is explicit, and a key never reads more than what was ticked. Cost: 8 rows + the locked line is over check 4's seven on a phone — it scrolls once, with the Next button sticky; on the laptop (where this screen is actually used) all 8 fit.

B (last phone): three presets first (Catalog only · A POS or printer · A vendor portal), "Custom…" opening the 8-row list. Fits seven; but a preset's own contents are a sentence to read, the names are Veritill's guess at integrations it has not met yet, and a preset that silently includes Sales (costs) is the kind of over-grant §4.11 warns against.

The eight checks (screens.md §0, plus 9 and 10)

#CheckScoreEvidence
1One job, action visible✓Panel: one primary button, New key, under the rows (visible without scrolling at 2–3 keys; it rides at the foot of the panel, not the page). Each New-key screen: one sticky Next / Create. Shown-once: Copy is the one action; Done waits for it.
2No paragraphs✓Longest line on any screen is the switch's own "Metered calls go on the Pro plan bill" (8 words) and the revoke dialog's two sentences (13 words), the same length the list's existing Suspend / Cancel dialogs already use. Why the four groups are locked is behind ⓘ.
3A picture on every row, the same everywhere△Group rows and key rows reuse the shipped icon files (products, vendors, invoices, count, purchasing, pricing, catering, dayclose, register, money, team, settings, warning, cancel, done). A key's own picture is its integration's group icon (the printer key wears Pricing, the Toast key wears Register) — a stored logo per integration would be better and is named, not drawn. Four NEW meanings need a file before build: key, copy, lock, log (drawn inline here in the same line style).
4≤ 7 things on a phone△Panel (phone 2): switch · 3 key rows · audit line · New key = 6 ✓. Step 2 and shown-once: ≤ 5 ✓. Step 1 (Option A): name + 8 group rows + the locked line = 10 — over, by the product's own group count; scrolls once with Next sticky. Option B fits 7 at the cost named above. On a laptop every key fact is in one grid row with nothing behind a tap (check 4's own admin rule).
5Under 300 ms✓One read per panel open: the client's api_keys rows (name, scopes, limits, expires_at, last_used_at, created_by, revoked_at) plus one count per key for "calls this month" — a metered counter the auth hook already has to keep (usage metered), never computed on open. The audit rows load only when "N this month ▸" is tapped. The list itself stays as it is today.
6A way back✓"‹ Clients" on the panel; "‹ API" on step 1; "‹ 1 of 2" on step 2; Done on the shown-once screen lands back on the panel with the new row highlighted (phone 6). Admin › Clients is itself one tap from the app's gear.
7One home per function✓The entitlement switch moves INTO the panel (the row's Enable / Turn off button goes) — one place for the switch, the keys and the audit line. The client's own ApiKeyCard keeps showing the one transition key until api_keys replaces it (build item 2); once scoped keys exist it reads only, never a second place to make one.
8As few screens as possible✓No new route: a panel under the existing row, two short New-key screens that are a drawer flow over the same page, the shipped step-up sheet and confirm dialog reused as they are. Alternatives considered: a /admin/clients/[id] page — rejected, nothing else about a client needs one yet.
9For someone who does not read✓Where am I: the client's initials and name at the top of every screen in the flow. What is happening: the switch's colour, a stopped key struck through and grey, the green "Key made" ring. What next: exactly one primary button per screen. The key value is an obvious example string, never a real one.
10Walked, not reasoned△Platform plane only — not on the first-five-minutes path, so the fresh-persona walk does not reach it. The build's own e2e (issue acceptance: "the admin view e2e on the fixture") should walk the exact sequence of phones 2 → 3 → 4 → 5 → 6: a key made with Products · Read, shown once, copied, then revoked, the audit line counting both.

Where every number comes from (build items 2–3 of #1085, once this is approved)

api_keys (Core migration, columns as the issue names them) draws the rows; scopes jsonb {fn: 'View'|'Edit'} renders as the group words through §4.11's own table (Items + Item Model read → "Products and catalog", Reports → "Sales and reports", …); rate_per_min / page_cap / expires_at / last_used_at / created_by / revoked_at are the row's other columns verbatim. "Calls this month" needs a per-key metered counter the issue's own "usage metered" line already asks for — named for Core as part of the migration comment, not guessed here (a count column advanced with the 5-minute last_used_at throttle, or a monthly row — Core's call). The audit line reads the existing audit rows for the key's name (the issue's own "audit rows carry the key's name"). The switch is settings.api.enabled (#1046, shipped). The step-up sheet and the confirm dialog are shipped components, unchanged.
