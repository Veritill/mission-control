Against the eight screens.md §0 checks

1. One job"Keep our prices in line with named competitors": the Compare tab is the verdict, the Basket tab is what feeds it, the walk pill is how a fresh tag gets recorded. One job, three necessary views of it — never an unrelated second function bolted on.
2. No paragraphsEvery row is one line (name + gap, or name + competitors chip); the "why" for a gap is the competitor name and dollar figure only, nothing longer.
3. Icon on every row🍅🧅🥛🍚🫘🫓 per item (the same family pictures Products/Ingredients already use), 📈 dearer / 📉 cheaper, 🚶 the walk, 🏷️ the entry card — same icon, same meaning, everywhere.
4. ≤7 things on a phoneCompare tab: the summary card (1) + up to 5 dearer/cheaper rows before scrolling (2). Basket tab: the walk pill (1) + Add button (2) + up to 5 basket rows (3). Nothing computed beyond what already scrolls into view.
5. Fast, no on-open summaryThe whole screen is one read: GET /price-watch/today for Compare (already the finished comparisonCard arithmetic) and GET /price-watch/basket + GET /price-watch/summary for Basket — no client-side recomputation of a ceiling or a gap, the server already did it.
6. A way back← at top returns to Pricing, named there; Price watch is one tap from Pricing, which is one tap from Work.
7. One home per functionThis is the ONE screen for the basket, the comparison and the walk link — Pricing's card is a teaser, never a second editor; My tasks keeps showing the walk task in its own queue as it does every other task, this screen's pill just jumps straight to it.
8. As few screens as possibleThe entry is a card on the existing Pricing screen (rule 8: a card before a new screen), and the walk itself opens as a bottom sheet here rather than a fourth screen, reusing the exact per-line record shape POST /tasks/:id/walk already supports.

Field map (matches priceWatch.ts / routes/priceWatch.ts today)

Compare tabGET /price-watch/today → card: basketCount, comparedCount, dearer[]/cheaper[] (id, name, baseUnit, ourPrice, competitor, competitorPrice, gapUsd, gapPct, icon), basketTotal, competitorTotal, lastWalkDate.
Basket tabGET /price-watch/basket (rows to edit) + GET /price-watch/summary (current price + per-competitor latest/ceiling for the meta line); POST/PATCH /price-watch/basket[/:id] add/edit, no delete route today — the mockup's ✕ deactivates (active:false), matching what PATCH already accepts, rather than a hard delete the API does not offer.
Add item pickerSearches the existing catalog (items) and the ingredient list the same way Ingredients' own picker does; no new search endpoint — a real build reuses GET /items?q=.
Walk pill + sheetPOST /price-watch/walk builds/refreshes the week's task; the sheet lists its lines[] (name, competitor, done, price/unit if answered); POST /tasks/:id/walk records one line by hand (a photo lane exists server-side too, reusing the invoice reader — left out of this mockup's quick-entry sheet, since a camera capture flow already has its own pattern in Load invoice and doesn't need re-designing here).
