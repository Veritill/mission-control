Against the eight screens.md §0 checks

1. One jobOne block, one job: show the agent's last action and let the customer answer the one open question. No second surface — the Review inbox drops the onboarding_ask kind entirely.
2. No paragraphsEach part of the card is one short line: the "did" line, the ask, the one-line why (behind the ⓘ tap, not shown by default), each history row. The longest text on screen is the why line, one sentence.
3. Icon on every row🤖 the agent avatar on the card, 📎 the upload action, ✓ every history row, the field's own unit label beside the number.
4. ≤7 things on screenThe card itself never exceeds: did-line, ask, why-tap, one input/drop, two buttons, plus up to 3 history rows — 7 at most, and history collapses to a one-line count once there is more than that (state 2 shows "2 answered" fully since it fits; a longer history would read "N answered · see all").
5. Fast, no on-open summaryThe card reads the same onboarding_ask row and agent_runs.lastStep/counts GET /tenant/onboarding already computes server-side (#418) — no new aggregation on open.
6. A way back← Settings on every state; this is a block on the existing Getting started screen, not a new screen, so the existing back link is unchanged.
7. One home per functionAnswering an ask happens ONLY here now. The Review inbox stops rendering onboarding_ask rows (Kiran, #410: "I don't like using My tasks for any communication with the onboarding agent"); the chef's cards and standing cost cards stay in the inbox since those are operations, not setup.
8. As few screens as possibleZero new screens. The upload action reuses the existing Invoices file/camera door; "Connect Toast" (not shown here, covered by #418) links to the existing Toast settings screen; every other door already exists.
